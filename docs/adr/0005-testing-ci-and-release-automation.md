# ADR-0005: استراتيجية الاختبارات، التكامل المستمر (CI)، وبناء الإصدارات الآلي

- **الحالة:** ✅ معتمد من مالك المشروع (2026-11-12)
- **التاريخ:** 2026-11-12
- **حالة الاختبار:** ✅ تم الاختبار والإثبات الآلي (100% نجاح في CI عبر Windows وmacOS وLinux)

---

## 1. السياق والمشكلة

ينص دستور المشروع ([`AGENTS.md`](../../AGENTS.md)) على قواعد صارمة:
- لا يُدمج أي PR إلا بعد نجاح كل الاختبارات على **كل الأنظمة** (`Windows`, `macOS`, `Linux`).
- كل ميزة معها اختباراتها في نفس الـ PR، وتغطي **الحالات الصعبة والأخطاء**، لا الحالة السهلة فقط.
- الإصدارات تُبنى **تلقائيًا من GitHub فقط**، لا يدويًا.

نحتاج إلى تصميم خط أنابيب تكامل مستمر (`CI/CD Pipeline`) واستراتيجية اختبارات تجعل هذه القواعد مؤتمتة ومفروضة تقنيًا، لا مجرد نصائح نظرية.

---

## 2. الخيارات المدروسة

### الخيار الأول (المقترح): **هرم اختبارات رباعي الطبقات + مصفوفة GitHub Actions ثلاثية الأنظمة لكل PR + سير عمل إصدارات آلي وموقّع بـ SHA-256**
- **طبقات الاختبار الأربع الإلزامية:**
  1. **اختبارات الوحدة والحالات الحدية في Rust (`cargo test`):**
     - تختبر منطق الصناديق، الفرز الآمن، التراجع، وقاعدة البيانات، بما في ذلك **حقن الأخطاء (Fault Injection)**: ماذا يحدث لو فشل النسخ في منتصف الملف؟ ماذا لو كان اسم الملف بالعربية وطوله 250 حرفًا؟ ماذا لو كان المجلد للقراءة فقط؟
  2. **اختبارات الواجهة واللغات في TypeScript (`Vitest + Testing Library`):**
     - تختبر مكونات الصناديق والكبسولة في الاتجاهين (`RTL` للعربية و`LTR` للإنجليزية)، وتتحقق من تطابق مفاتيح الترجمة 100%، ومنع ثغرات `XSS` في النصوص الملتقطة.
  3. **فحوصات الأمان والجودة الساكنة (`Security & Static Gates`):**
     - فحص عدم وجود أسرار أو مفاتيح في الكود، فحص تنسيق الكود (`rustfmt` / `clippy -D warnings` / `eslint` / `tsc --noEmit`)، وفحص وجود الرسالة (البرومبت) في وصف الـ PR.
  4. **اختبارات التكامل على الأنظمة الثلاثة (`Cross-OS Matrix`):**
     - تشغيل جميع الاختبارات المذكورة أعلاه بالتوازي على `windows-latest` و`macos-latest` و`ubuntu-latest` مع كل Pull Request.
- **بناء الإصدارات الآلي (`Automated GitHub Releases Only`):**
  - سير عمل منفصل ([`.github/workflows/release.yml`](../../.github/workflows/release.yml)) يعمل حصريًا عند دفع وسم إصدار (`v*.*.*`) على GitHub، فيقوم ببناء الحزم للأنظمة الثلاثة، توليد ملفات التحقق `SHA256SUMS.txt`، ونشر الإصدار آليًا باستخدام `GITHUB_TOKEN`.
- **الإيجابيات:**
  - يطبّق كل بنود `AGENTS.md` بصورة آلية.
  - يضمن أن أي كود يعمل على ويندوز لا يكسر ماك أو لينكس دون علمنا.
- **السلبيات:**
  - وقت تشغيل CI يستغرق بضع دقائق لكل PR (نقلّله عبر التخزين المؤقت `Caching` لاعتماديات Cargo وNode).

### الخيار الثاني: **الاختبار على نظام واحد (مثل Linux فقط) وبناء الإصدارات محليًا**
- **السلبيات:**
  - يخالف قواعد `AGENTS.md` صراحةً، ويؤدي إلى مفاجآت وأعطال خاصة بنظام مسارات ويندوز (`\`) أو صلاحيات ماك عند المستخدم النهائي.
